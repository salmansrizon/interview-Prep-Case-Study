## 1. Topic: Structured Outputs & Frameworks — Getting JSON from LLMs, LangChain

Class 1-এ আমরা LLM-কে ভালো টেক্সট জেনারেট করতে শিখিয়েছি। কিন্তু বেশিরভাগ প্রোডাকশন সিস্টেমে LLM-এর আউটপুট মানুষ পড়ে না — আরেকটা প্রোগ্রাম সেটা পড়ে, ডেটাবেসে সেভ করে, বা অন্য একটা সিস্টেমে পাঠায়। তার জন্য LLM-এর আউটপুট **টেক্সট** না হয়ে **স্ট্রাকচার্ড ডেটা** (JSON) হতে হয়। এই ক্লাসে আমরা শিখব:

* **Getting JSON from LLMs** — কীভাবে LLM-কে বাধ্য করা যায় সবসময় একটা নির্দিষ্ট ফরম্যাটে (স্কিমা) আউটপুট দিতে।
* **LangChain** — LLM অ্যাপ্লিকেশন বানানোর একটা ফ্রেমওয়ার্ক, যা প্রম্পট, মডেল কল, এবং আউটপুট পার্সিং-কে একসাথে "chain" করে।
* **Prompt Templates** — পুনরায় ব্যবহারযোগ্য প্রম্পট গঠন, যেখানে ভ্যারিয়েবল বসানো যায়।
* **Chains of Reasoning** — একাধিক LLM কল বা ধাপকে একসাথে জুড়ে একটা জটিল কাজ সম্পন্ন করা।

**Project Goal:** একটা **Resume-to-JSON** কনভার্টার বানানো, যেটা একটা সিভি (CV) পড়ে তার ভেতর থেকে অভিজ্ঞতা, স্কিল, এডুকেশন — সবকিছু একটা পরিষ্কার, ডেটাবেসে-সেভ-করার-উপযোগী JSON ফরম্যাটে বের করে আনবে।

## 2. Why It Is Related

একটা ATS (Applicant Tracking System) বা রিক্রুটমেন্ট প্ল্যাটফর্ম যখন হাজার হাজার সিভি প্রসেস করে, তখন সেই ডেটা একটা ডেটাবেসে সার্চেবল, ফিল্টারযোগ্য ফরম্যাটে থাকতে হয় — "৫ বছর Python অভিজ্ঞতা আছে এমন সব ক্যান্ডিডেট দেখাও" — এই ধরনের কোয়েরি চালানো সম্ভব হয় শুধু তখনই, যখন ডেটা স্ট্রাকচার্ড থাকে। LLM দিয়ে unstructured টেক্সট (সিভির ফ্রি-ফর্ম লেখা) থেকে structured ডেটা বের করা — এই প্যাটার্নটাই **Information Extraction**, এবং এটা ইনভয়েস প্রসেসিং, মেডিকেল রেকর্ড পার্সিং, কন্ট্র্যাক্ট অ্যানালাইসিস — এরকম অসংখ্য রিয়েল-ওয়ার্ল্ড এআই অ্যাপ্লিকেশনের ভিত্তি। Week 10-এ আমরা CV থেকে "অর্থ" বের করেছিলাম (semantic matching); এখন আমরা CV থেকে "ডেটা" বের করছি (structured extraction) — দুটোই ভিন্ন কিন্তু পরিপূরক স্কিল।

## 3. How It Works

### 3.1 Getting JSON from LLMs — তিনটা পদ্ধতি

```
পদ্ধতি ১: Prompt Engineering (সবচেয়ে সহজ, সবচেয়ে কম নির্ভরযোগ্য)
    "নিচের ফরম্যাটে JSON আউটপুট দাও: {...}"
    → মডেল প্রায়ই মেনে চলে, কিন্তু মাঝেমধ্যে অতিরিক্ত টেক্সট
      যোগ করে ফেলে বা ফরম্যাট সামান্য ভুল করে।

পদ্ধতি ২: Structured Output Mode (বেশি নির্ভরযোগ্য)
    মডেল/API-কে সরাসরি বলা "শুধু এই স্কিমা অনুযায়ী JSON দাও"
    → মডেল প্রোভাইডার নিজেই আউটপুট ভ্যালিডেট করে নিশ্চিত করে।

পদ্ধতি ৩: Output Parser + Retry (সবচেয়ে রোবাস্ট)
    মডেলের আউটপুট নিয়ে JSON হিসেবে parse করার চেষ্টা করা,
    ব্যর্থ হলে এরর মেসেজসহ মডেলকে আবার জিজ্ঞেস করা।
```

আমাদের প্রজেক্টে (লোকাল LLM, Ollama) আমরা পদ্ধতি ১ আর ৩ মিলিয়ে ব্যবহার করব — একটা কড়া প্রম্পট (স্কিমা উদাহরণসহ) দিয়ে শুরু, তারপর আউটপুট parse করে ব্যর্থ হলে retry করা।

### 3.2 LangChain — কেন একটা ফ্রেমওয়ার্ক লাগে?

সরাসরি Ollama/OpenAI API কল করে একটা সিম্পল টাস্ক করা সহজ, কিন্তু একটা রিয়েল অ্যাপ্লিকেশনে প্রায়ই লাগে: প্রম্পট টেমপ্লেট রিইউজ করা, আউটপুট পার্স করা, একাধিক ধাপ চেইন করা, এরর হ্যান্ডেল করা, রিট্রাই লজিক — এই সব বারবার হাতে লেখা ক্লান্তিকর ও বাগ-প্রবণ। **LangChain** এই কমন প্যাটার্নগুলোর জন্য রেডিমেড বিল্ডিং ব্লক দেয়:

```
PromptTemplate ──▶ LLM (Ollama) ──▶ Output Parser ──▶ Structured Result
      │                  │                  │
   ভ্যারিয়েবল          মডেল কল          JSON/Pydantic
   বসানো                                  অবজেক্টে রূপান্তর
```

### 3.3 Prompt Templates — পুনরায় ব্যবহারযোগ্য প্রম্পট

```python
from langchain_core.prompts import PromptTemplate

template = PromptTemplate.from_template(
    "নিচের সিভি থেকে নাম, স্কিল, এবং কাজের অভিজ্ঞতা বের করে "
    "JSON আকারে দাও:\n\n{resume_text}"
)

prompt = template.format(resume_text="John Doe, Python developer...")
```

Template ব্যবহার করলে একই প্রম্পট স্ট্রাকচার হাজারটা ভিন্ন CV-তে reuse করা যায়, কোড রিপিট না করে — ঠিক যেমন একটা ফাংশন একবার লিখে বারবার কল করা হয়।

### 3.4 Chains of Reasoning — একাধিক ধাপ জোড়া লাগানো

জটিল কাজ প্রায়ই একটা LLM কলে ভালোভাবে হয় না — ভাগ করে করা ভালো:

```
Step 1: Extract raw sections (Experience, Skills, Education) — separate LLM call
Step 2: Structure each section into JSON fields — separate LLM call
Step 3: Validate & merge into final schema — code, not LLM
```

এটাকে বলে **Chaining** — একটা ধাপের আউটপুট পরের ধাপের ইনপুট হয়। LangChain-এর `Runnable`/`|` (pipe) সিনট্যাক্স এই চেইনগুলো পরিষ্কারভাবে লেখার সুযোগ দেয়:

```python
chain = extract_prompt | llm | json_parser
result = chain.invoke({"resume_text": cv_text})
```

## 4. Details & Valid Points

### 4.1 Why Not Just Regex/Rule-Based Extraction?

CV-র ফরম্যাট অসংখ্য রকম — কেউ "Skills:" লেখে, কেউ "Technical Proficiencies", কেউ বুলেট পয়েন্ট ব্যবহার করে, কেউ প্যারাগ্রাফ। রেগুলার এক্সপ্রেশন বা ফিক্সড রুল দিয়ে এই বৈচিত্র্য কভার করা প্রায় অসম্ভব — প্রতিটা নতুন ফরম্যাটের জন্য নতুন রুল লিখতে হবে। LLM-ভিত্তিক এক্সট্রাকশন **অর্থ** বোঝে, ফরম্যাট না — তাই "Technical Proficiencies" আর "Skills" দুটোকেই একই ফিল্ডে ম্যাপ করতে পারে, নতুন রুল ছাড়াই।

### 4.2 Schema Validation — নিশ্চিত হওয়া যে আউটপুট সঠিক গঠনের

শুধু "JSON পার্স হলো কিনা" যথেষ্ট না — আউটপুটে সঠিক ফিল্ড আছে কিনা, সঠিক টাইপ আছে কিনা (যেমন `years_experience` একটা সংখ্যা, স্ট্রিং না) — এটাও যাচাই করা জরুরি। **Pydantic** মডেল ব্যবহার করে এই স্কিমা ভ্যালিডেশন স্বয়ংক্রিয় করা যায় — ভুল ফরম্যাট এলে সাথে সাথে ধরা পড়ে, সাইলেন্টলি ভুল ডেটা ডেটাবেসে ঢুকে যাওয়ার আগেই।

### 4.3 Retry Strategy — মডেল ভুল করলে কী করবেন

লোকাল LLM (৮B প্যারামিটার) মাঝেমধ্যে অসম্পূর্ণ বা ভুল-ফরম্যাটেড JSON দিতে পারে (বড় ক্লাউড মডেলের তুলনায় বেশি হতে পারে)। তাই একটা robust পাইপলাইনে থাকে: (১) parse করার চেষ্টা, (২) ব্যর্থ হলে "তোমার আগের আউটপুট ভ্যালিড JSON ছিল না, আবার চেষ্টা করো" — এই ফিডব্যাকসহ আবার কল করা, (৩) নির্দিষ্ট সংখ্যক (যেমন ৩বার) চেষ্টার পরও ব্যর্থ হলে ইউজারকে জানানো, silently ভুল ডেটা না দেওয়া।

## 5. Related Analogy: The Data Entry Clerk

> কল্পনা করুন একজন ডেটা এন্ট্রি ক্লার্ক, যিনি হাতে-লেখা ফর্ম পড়ে সেগুলো একটা স্প্রেডশিটে টাইপ করেন।

| Concept | Data Entry Clerk Analogy |
| --- | --- |
| **Unstructured → Structured** | হাতে-লেখা ফর্ম (যেকোনো হাতের লেখা, যেকোনো ভাষায় টীকা) পড়ে একটা ফিক্সড-কলাম স্প্রেডশিটে টাইপ করা। |
| **Prompt Template** | ক্লার্কের সামনে একটা স্ট্যান্ডার্ড চেকলিস্ট থাকা — "নাম কোথায় লেখা, ফোন নম্বর কোথায় লেখা" — প্রতিটা ফর্মে একই চেকলিস্ট ব্যবহার করা। |
| **Schema Validation** | সুপারভাইজার এন্ট্রি জমা দেওয়ার আগে চেক করছেন — ফোন নম্বরের কলামে আসলেই সংখ্যা আছে তো? নাকি ভুলে নাম লেখা হয়ে গেছে? |
| **Retry Strategy** | ক্লার্ক যদি ভুল এন্ট্রি করে, সুপারভাইজার সেটা ফেরত পাঠান "এই কলামটা আবার ঠিক করো" বলে, বাতিল করে না দিয়ে। |
| **LangChain (as a framework)** | পুরো অফিসের জন্য একটা স্ট্যান্ডার্ড ওয়ার্কফ্লো টুল, যা প্রতিটা ক্লার্কের জন্য আলাদা করে চেকলিস্ট-বানানো, ভ্যালিডেশন, রিট্রাই — সব বারবার হাতে লেখার বদলে রেডিমেড দেয়। |

## 🧠 Brain Teasers & Exercises (নিজে চেষ্টা করুন)

1. **Schema Design**: একটা CV থেকে কী কী ফিল্ড বের করা "যথেষ্ট" মনে করেন? `years_experience` কি একটা নাকি প্রতিটা জব-এর জন্য আলাদা হওয়া উচিত? আপনার স্কিমা ডিজাইন করুন।
2. **Ambiguous CV Test**: এমন একটা CV স্নিপেট ভাবুন যেখানে "স্কিল" আর "অভিজ্ঞতা" আলাদা করা কঠিন (যেমন "৩ বছর ধরে Python ব্যবহার করে ডেটা পাইপলাইন বানিয়েছি")। LLM কীভাবে এটাকে দুই ফিল্ডে ভাগ করবে বলে মনে হয়?
3. **Retry Limit**: যদি ৩ বার চেষ্টার পরও মডেল ভ্যালিড JSON দিতে না পারে, প্রোডাকশন সিস্টেমে তখন কী করা উচিত — ইউজারকে এরর দেখানো, নাকি আংশিক ডেটা সেভ করে "ম্যানুয়াল রিভিউ প্রয়োজন" ফ্ল্যাগ করা? কোনটা বেশি ব্যবহারিক?
