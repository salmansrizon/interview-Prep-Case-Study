## 1. Topic: RAG Pipelines — Combining LLMs with Vector Databases

Class 1-এ আমরা শিখেছি কীভাবে ডকুমেন্ট চাঙ্ক করে ভেক্টর ডেটাবেসে ইনডেক্স করতে হয়, আর সেখান থেকে সিমেন্টিক সার্চ করতে হয়। এই ক্লাসে আমরা সেই Retrieval-কে Week 11-এর LLM (Ollama) এর সাথে জুড়ে দেব — এই কম্বিনেশনটার নাম **Retrieval-Augmented Generation (RAG)**। এই ক্লাসে আমরা শিখব:

* **RAG Architecture** — কীভাবে Retrieval আর Generation একসাথে কাজ করে একটা নির্ভরযোগ্য প্রশ্ন-উত্তর সিস্টেম তৈরি করে।
* **The "Open-Book Exam" Analogy** — কেন RAG একটা মডেলকে বেশি নির্ভুল আর কম "মনগড়া" বানায়।
* **Metadata Filtering** — নির্দিষ্ট ডকুমেন্ট বা সেকশনে সার্চ সীমাবদ্ধ রাখা।

**Project Goal:** একটা **Local Document Q&A Bot** বানানো, যেটা আপলোড করা PDF থেকেই কড়াকড়িভাবে প্রশ্নের উত্তর দেবে — নিজে থেকে কিছু "বানিয়ে" বলবে না।

---

## 2. Why It Is Related

Week 11-এ আমরা দেখেছি LLM দারুণ টেক্সট জেনারেট করতে পারে — কিন্তু একটা বড় সমস্যা আছে: LLM তার ট্রেনিং ডেটার ওপর ভিত্তি করে উত্তর দেয়, যা কখনো কখনো পুরনো, ভুল, বা সম্পূর্ণ "বানানো" (hallucination) হতে পারে। যদি আপনি জিজ্ঞেস করেন "আমাদের কোম্পানির ছুটির নীতি কী?", LLM কোম্পানির আসল হ্যান্ডবুক কখনো দেখেইনি — তাই সে হয় "আমি জানি না" বলবে, নয়তো একটা সাধারণ-সাধারণ উত্তর "বানিয়ে" দেবে যেটা আপনার কোম্পানির জন্য ভুল হতে পারে।

**RAG এই সমস্যার সমাধান**: প্রশ্নের উত্তর দেওয়ার আগে, প্রথমে ভেক্টর ডেটাবেস থেকে প্রাসঙ্গিক তথ্য (Class 1-এর কাজ) খুঁজে বের করে, তারপর সেই তথ্যটা LLM-কে "এই তথ্যের ভিত্তিতে উত্তর দাও" বলে দেওয়া হয়। এভাবে LLM নিজের মেমোরি থেকে অনুমান না করে, **আসল ডকুমেন্ট পড়ে** উত্তর দেয় — অনেকটা ওপেন-বুক পরীক্ষার মতো।

## 3. How It Works

### 3.1 The RAG Pipeline

```
User Question: "How many sick leave days do I get?"
       │
       ▼
[1] EMBED the question (same model as Class 1: paraphrase-MiniLM-L3-v2)
       │
       ▼
[2] RETRIEVE top-K similar chunks from ChromaDB
       │        (optionally filtered by metadata — e.g. only "hr_policy.pdf")
       ▼
[3] AUGMENT the prompt — inject retrieved chunks as context:

    "নিচের ডকুমেন্ট অংশগুলোর ভিত্তিতে শুধু প্রশ্নের উত্তর দাও।
     উত্তর ডকুমেন্টে না থাকলে 'ডকুমেন্টে এই তথ্য পাওয়া যায়নি' বলো।

     Context: [chunk 1] [chunk 2] [chunk 3]
     Question: How many sick leave days do I get?"
       │
       ▼
[4] GENERATE — Ollama (llama3.1:8b) পড়ে উত্তর তৈরি করে, শুধু দেওয়া context থেকে
       │
       ▼
Answer + Citations (কোন ডকুমেন্ট, কোন পেজ থেকে তথ্য এসেছে)
```

### 3.2 The "Open-Book Exam" Analogy — কেন এটা কাজ করে

একটা সাধারণ (non-RAG) LLM প্রশ্নের উত্তর দেয় **বন্ধ বই পরীক্ষার (Closed-Book Exam)** মতো — শুধু নিজের মুখস্থ জ্ঞান (ট্রেনিং ডেটা) দিয়ে, যা ভুল বা পুরনো হতে পারে। RAG সিস্টেম প্রশ্নের উত্তর দেয় **খোলা বই পরীক্ষার (Open-Book Exam)** মতো — উত্তর দেওয়ার ঠিক আগে প্রাসঙ্গিক পাতাগুলো (retrieved chunks) সামনে খুলে দেওয়া হয়, আর মডেলকে বলা হয় শুধু সেই পাতা থেকেই উত্তর লিখতে। এতে দুটো বড় সুবিধা:

1. **নির্ভুলতা বাড়ে** — মডেল অনুমান না করে আসল টেক্সট থেকে উত্তর টানে।
2. **Hallucination কমে** — যদি উত্তরটা "বইয়ের পাতায়" (retrieved context) না থাকে, মডেলকে স্পষ্ট নির্দেশ দেওয়া থাকে "না জানি বলো", বানিয়ে বলো না।

### 3.3 Metadata Filtering — নির্দিষ্ট ডকুমেন্টে সার্চ সীমাবদ্ধ রাখা

Class 1-এ আমরা প্রতিটা চাঙ্কের সাথে metadata (source filename, page) সেভ করেছিলাম। এখন সেটা কাজে লাগবে — ইউজার যদি একাধিক ডকুমেন্ট আপলোড করে (যেমন "HR Policy.pdf" আর "IT Guidelines.pdf"), তাহলে সার্চ **সব ডকুমেন্টে** না চালিয়ে ইউজারকে বেছে নিতে দেওয়া যায় শুধু একটা নির্দিষ্ট ডকুমেন্টে সার্চ করতে:

```python
results = collection.query(
    query_embeddings=[query_vector],
    n_results=3,
    where={"source": "hr_policy.pdf"},  # metadata filter
)
```

এটা শুধু সুবিধার জন্য না — এটা **নির্ভুলতাও বাড়ায়**। যদি ইউজার নির্দিষ্টভাবে "HR পলিসি" নিয়ে জিজ্ঞেস করে, কিন্তু সিস্টেম ভুলে "IT Guidelines" থেকেও চাঙ্ক নিয়ে আসে, উত্তর বিভ্রান্তিকর হতে পারে। Metadata filter এই noise কমায়।

## 4. Details & Valid Points

### 4.1 Why "Strictly From Documents" Needs an Explicit Guardrail

শুধু context দিয়ে দিলেই যথেষ্ট না — LLM-কে **স্পষ্টভাবে** নির্দেশ দিতে হয় যে সে যেন শুধু দেওয়া context ব্যবহার করে, নিজের সাধারণ জ্ঞান না মেশায়। System prompt-এ এই ধরনের নির্দেশনা থাকা জরুরি:

```
"তুমি শুধু নিচের CONTEXT থেকেই উত্তর দেবে। CONTEXT-এ উত্তর না
থাকলে স্পষ্টভাবে বলবে 'এই তথ্য ডকুমেন্টে পাওয়া যায়নি' —
কখনো নিজের জ্ঞান থেকে অনুমান করে উত্তর দেবে না।"
```

এটা Week 11-এর Prompt Engineering-এর সরাসরি প্রয়োগ — একটা ভালো-ডিজাইন করা system prompt ছাড়া RAG পাইপলাইন থাকলেও মডেল context উপেক্ষা করে নিজের মতো উত্তর দিতে পারে।

### 4.2 Retrieval Quality — "Garbage In, Garbage Out" আবার

যদি Class 1-এর retrieval ধাপ ভুল/অপ্রাসঙ্গিক চাঙ্ক নিয়ে আসে, তাহলে যত ভালো LLM-ই ব্যবহার করুন না কেন, উত্তর ভুল হবে — কারণ মডেল ভুল "বই পাতা" পড়ছে। তাই RAG সিস্টেমের মান নির্ভর করে দুটো জিনিসের ওপর: (১) Retrieval কতটা প্রাসঙ্গিক চাঙ্ক আনতে পারছে (Class 1-এর চাঙ্কিং/এমবেডিং কোয়ালিটি), (২) Generation কতটা বিশ্বস্তভাবে শুধু সেই চাঙ্ক থেকেই উত্তর তৈরি করছে (এই ক্লাসের প্রম্পট ডিজাইন)।

### 4.3 Top-K — কয়টা চাঙ্ক যথেষ্ট?

খুব কম চাঙ্ক (K=1) আনলে গুরুত্বপূর্ণ প্রাসঙ্গিক তথ্য বাদ পড়ে যেতে পারে। খুব বেশি চাঙ্ক (K=20) আনলে LLM-এর কনটেক্সটে অপ্রয়োজনীয় তথ্যের ভিড়ে আসল উত্তর "হারিয়ে" যেতে পারে, আর প্রসেসিং সময়ও বাড়ে। ব্যবহারিকভাবে K=3 থেকে K=5 সাধারণত ভালো ব্যালেন্স দেয়।

## 5. Related Analogy: The Open-Book Exam (Extended)

> কল্পনা করুন একজন স্টুডেন্ট একটা ওপেন-বুক পরীক্ষা দিচ্ছেন।

| RAG Concept | Open-Book Exam Analogy |
| --- | --- |
| **Vector DB (Class 1)** | পুরো বইটা আগে থেকেই ইনডেক্স করে রাখা (সূচিপত্র বানানো), যাতে পরীক্ষার সময় দ্রুত সঠিক পাতা খুঁজে পাওয়া যায়। |
| **Retrieval** | পরীক্ষার প্রশ্ন পড়ে বইয়ের ঠিক কোন ৩টা পাতা এই প্রশ্নের সাথে প্রাসঙ্গিক তা বের করা। |
| **Augmentation** | সেই ৩টা পাতা খুলে নিজের ডেস্কে সামনে রাখা, উত্তর লেখার আগে। |
| **Generation** | সেই খোলা পাতাগুলো পড়ে উত্তর লেখা — মুখস্থ বিদ্যা থেকে না লিখে। |
| **"Strictly from documents" guardrail** | পরীক্ষকের নিয়ম: "শুধু বইয়ে যা লেখা আছে তাই লিখবে, নিজের বাইরের জ্ঞান থেকে কিছু যোগ করবে না।" |
| **Metadata Filtering** | পরীক্ষায় বলা "শুধু অধ্যায় ৩ থেকে উত্তর দাও" — পুরো বই না ঘেঁটে একটা নির্দিষ্ট অংশে মনোযোগ দেওয়া। |
| **Citations** | উত্তরের পাশে "পাতা ৪৫ অনুযায়ী..." লিখে দেওয়া — যাতে পরীক্ষক (বা ইউজার) নিজে গিয়ে যাচাই করতে পারেন। |

## 🧠 Brain Teasers & Exercises (নিজে চেষ্টা করুন)

1. **Hallucination Test**: এমন একটা প্রশ্ন করুন যার উত্তর আপলোড করা ডকুমেন্টে নেই (যেমন সম্পূর্ণ অসম্পর্কিত বিষয়)। সিস্টেম কি সততার সাথে "জানি না" বলে, নাকি বানিয়ে উত্তর দেয়?
2. **Top-K Experiment**: K=1 আর K=10 দিয়ে একই প্রশ্ন চালান। কোথায় উত্তরের মান সবচেয়ে ভালো, আর কোথায় খারাপ হতে শুরু করে?
3. **Metadata Filter Necessity**: দুটো ভিন্ন বিষয়ের ডকুমেন্ট আপলোড করুন (যেমন একটা HR পলিসি, একটা টেকনিক্যাল ম্যানুয়াল)। ফিল্টার ছাড়া আর ফিল্টার দিয়ে একই প্রশ্ন করে ফলাফলের পার্থক্য দেখুন।
